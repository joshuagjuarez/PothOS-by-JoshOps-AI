# Cognitive privacy requirements

Status: release requirements. Verify each mechanism on the actual published build.

## Custody and control

Private memory, original conversations, corrections, embeddings, indexes and
derived interpretations all require protection. Changing the representation
does not make personal information nonprivate.

The person should be able to inspect what is retained, correct it, choose
appropriate retention and export it through a documented recovery path.
Documentation must explain limits involving backups, copies and deletion.

Private signal should remain within the operator's permitted environment.
Project maintainers and commercial partners must not harvest it for profiling,
advertising, model training or sale. The purpose of support is to solve a
specific problem without collecting a person's inner life.

## Permissions and external connections

- Start a new installation with new operator-owned state and no founder grants.
- Enforce resource, account and tenant scope through actual mechanisms.
- Treat role names and hierarchy positions as responsibilities, not access grants.
- Make external processing visible and require a deliberate permitted choice.
- Measure network destinations for a local configuration and test failure behavior.
- Keep personal, family, organizational and community-project records separately scoped.

Do not claim that local hosting alone proves security or confidentiality.

## Support and voice

A report should show the sender exactly what will leave their environment.
Use a small synthetic reproduction wherever possible. Never require private
memory exports, credentials, recordings or case records for a public issue.

Voice paths need visible recording state, microphone permission, cancellation,
retention choices and clear disclosure of any external transcription or speech
service. Private voiceprints and personalized voice assets are excluded.

An automatic public Help Desk relay into the maintainer's private environment
has not been verified. Public issues and the documented contact are the current
feedback routes.

See [accessibility](ACCESSIBILITY.md) and [security reporting](../SECURITY.md).


## Clean release boundary

The reusable code and the founder's lived records are separate assets. A public
release must start with new user-owned state. Removing a visible profile card
is insufficient if private defaults, routes or records remain in the package.

The release export must exclude private profiles and biographies, original
conversation exports, memories and embeddings, venture/customer records, voices,
portraits, credentials, tokens, cookies, browser storage, logs, receipts, database
rows, backups and private repository history. Keep only reviewed reusable code,
schemas, templates and synthetic examples. Preserve the necessary copyright and
third-party notices without turning attribution into a runtime identity.

A new installation must not default to the founder's accounts, service grants,
private device addresses or privileged workspace. Its chosen backend and model
connection must be explicit. An unset connection must report its actual state.

The same generic tool can be available to different people without sharing their
data or authority. A business membership grants only the permissions that the
actual owner has given; leaving the business must not silently transfer an
independent personal history to the organization.

## Cognitive sovereignty and technical protection

The project opposes using private cognition for coercion, nonconsensual
surveillance, deceptive manipulation, discrimination or exploitation. Precise
prospective license conditions are being prepared separately. These requirements
do not amend earlier licenses or themselves create a universal runtime grant.

Technical protection must accompany the stated purpose: enforce scope at the
data/service boundary, minimize collection, show external processing, provide
revocation and recovery, and test with independent users. A software license
cannot guarantee that every operator obeys or replace these mechanisms.

No mandatory central copy of a person's memories or remote destruction of
independent local data is part of this release direction. A support request
should use the smallest permitted evidence needed for the selected problem.
